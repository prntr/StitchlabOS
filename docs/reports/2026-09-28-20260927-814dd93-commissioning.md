# Commissioning run: StitchLabOS 20260927-814dd93 on real hardware

> Dated evidence, 2026-09-28 and 2026-09-29. This report is never corrected
> afterwards; later findings go into a new report. The path under test is
> [11-commissioning.md](../11-commissioning.md) as of `814dd93` on
> `feat/cross-platform-stability`, plus checks 5–11 of the first run
> (`docs/reports/2026-09-27-v0.1.0-beta.4-commissioning.md` on branch
> `docs/beta4-commissioning-report`). Its purpose is to verify on hardware the
> fixes that run led to. Times on the Pi are BST (Europe/London, the image
> default); the operator's clock was one hour ahead.

## Result in one paragraph

The fixes from the first run hold on hardware. **Step 3 brought up the used
SKR Pico** on the second attempt: the script wrote Katapult with the old
application cleared, and Katapult then answered on the UART at once, which is
exactly where beta.4 failed. The first attempt failed because the Pico reached
flash mode two seconds after the script's 120-second wait ended. The image
reports its own version, its Update Manager shows no dirty repo and no
upstream Mainsail, the Wi-Fi scan works while the access point is active,
`live_jogd` no longer loops without a dongle, and Save & Start refuses a
design outside the frame without uploading it. New defects: the Wi-Fi manager
creates duplicate profiles and cannot hold AP mode, `live_jogd` ends up
`failed` from ordinary clicks, and Save & Start starts a job on an unhomed
machine. **The Beta2 acceptance is not met by this run**: the Pico was not
factory-fresh and the operator is one of the authors.

## Step 3 in detail

The human confirmed the 24 V switch was within reach and gave a separate
go-ahead for each attempt. Both ran as
`stitchlab-flash-pico 2>&1 | tee ~/flash-pico-run2{,b}.log` over `ssh -t`
from the Mac; the two logs are on the machine.

**Attempt 1, 2026-09-29 (BST).**

| Time | Event |
|---|---|
| 06:59:33 | `sudo` password asked, first thing |
| 06:59:37 | Klipper stopped; "Put the SKR Pico into flash mode (BOOTSEL)" with the four steps; wait for `RPI-RP2` begins |
| 07:01:37 | "No Pico appeared in BOOTSEL mode within 120s", "Continuing over the UART, assuming Katapult is already on the Pico." |
| 07:01:39 | kernel: `RP2 Boot` (`2e8a:0003`), `sda1` |
| 07:01–07:03 | UART attempts 1–3: `Detected Klipper binary version ce7002b`, `Attempting to connect to bootloader`, `FlashError: Error sending command [CONNECT] to Device`; then "Is Katapult on the Pico? If not: stitchlab-flash-pico --bootsel" |
| 07:03:22 | Klipper started: `mcu 'mcu': Unable to connect` |
| 07:06:25 | USB unplugged |

Switching on 24 V, fitting the jumper, plugging in a data cable and pressing
RESET took the human just over two minutes. The fallback to the UART is a
guess ("assuming Katapult is already on the Pico"), and here it was wrong: the
Pico was in the ROM bootloader, which does not answer on the UART. Entering
flash mode erases nothing, so the Pico kept its old Klipper.

**Attempt 2.** The human put the Pico into flash mode first; the agent
confirmed `2e8a:0003 Raspberry Pi RP2 Boot` and `RPI-RP2 -> sda1` at 07:09:21.

| Time | Event |
|---|---|
| 07:09:43 | Klipper stopped; "Found RPI-RP2 at /dev/sda1." and again "Found: /dev/sda1" |
| — | "Remove the BOOT jumper now (the Pico stays in flash mode), then press Enter"; jumper removed, Enter |
| 07:10:00–01 | mount, copy of the Katapult image with the application sector cleared, unmount; `USB disconnect` as the Pico reboots |
| — | "Katapult (old application cleared) written — the Pico rebooted." |
| — | UART attempt 1: `Katapult Connected`, `Software Version: … ec59b9b`, `Application Start: 0x10004000`, `Write complete: 168 pages`, `Verification Complete: SHA = C563B994D9B8C749055875F10255E646810E3C45`, `Programming Complete` |
| 07:10:23 | Klipper started; "OK — MCU connected.", "Done."; `/printer/info` `ready` |

This is the case the first run could not handle: a Pico with an older Klipper
at `0x10004000`. With the application cleared, Katapult found no application
and waited on the UART.

## Wi-Fi manager

**Save and connect creates two profiles.** NetworkManager's audit log, 23:03:14:

| Time | Operation | Profile |
|---|---|---|
| .081 | `connection-add-activate` | `c7ddbca9…` `StitchlabSRV`, from `_handle_connect` (`nmcli device wifi connect … password …`) |
| .412 | `connection-add` | `f58efb5e…` `StitchlabSRV`, from `_handle_add_network` |
| .486 | `connection-update` | `c7ddbca9…` |

`submitNetworkForm` awaits `addNetwork`, but that store action only emits
(`mainsail/src/store/server/wifiManager/actions.ts:210`), so `connect` is sent
at once and finds no saved profile. With two profiles of one name,
`nmcli connection show "StitchlabSRV"` in `wifi_status.sh` and
`wifi_profiles.sh` prints both: the SSID came out as
`"StitchlabSRV⏎StitchlabSRV"` and `autoconnect` as `false` although both were
`yes`. From 23:03:25 `server.wifi.status` and `server.wifi.profiles` failed
with `Invalid control character` (status line 5 column 26, profiles line 2
column 65). The human deleted the unused profile by UUID at 23:12:10; both
scripts produced valid JSON afterwards.

**AP mode does not hold.** 23:13:20–23 the page switched to AP mode
(`_handle_ap_enable`: `nmcli device disconnect wlan0`,
`nmcli connection up AccessPopup`). 23:13:34 `AccessPopup.timer` ran
(`OnUnitActiveSec=2min`), scanned, found `StitchlabSRV`, and logged "The
active profile AccessPopup is being disconnected"; 23:13:37 the Pi was back on
`StitchlabSRV`. The human saw the AP in the Mac's list but could not join it
in time. For the scan test the human ran `sudo accesspopup -a`, which stops the
timer; the AP then held. `sudo accesspopup` afterwards restored the timer and
`StitchlabSRV` (23:20:48). AccessPopup's own scan at 23:13:34, run while
`wlan0` was the AP, already listed the real networks.

## Deviations from 11-commissioning.md

1. **§1: an image that is not a release cannot use the `--repo` path.** Imager
   lists the latest release under the same name, and the card silently gets
   that one. A build under test needs *Use custom*, and nothing on the card or
   in Imager says which version was written; the Pi does
   (`/etc/stitchlabos_version`, Mainsail's `release_info.json`).
2. **§2: "reports no MCU" does not hold for a Pico that already runs matching
   firmware.** Klipper was `ready` on first boot.
3. **§3: the script's 120-second wait is shorter than the steps it asks
   for**, and when it runs out, the script assumes Katapult and goes on over
   the UART. Starting the script with the Pico already in flash mode works.
4. **§2: a reflashed card has a new host key**, and a Mac that knew the
   address refuses SSH until the old entry is removed (as in the first run for
   `stitchlab.local`).
5. **§4 checks motion only after homing.** It does not say that a job can be
   started on an unhomed machine; Klipper then refuses the first move.

## Correction to the first run's report

The first run's open issue 14 says GCode Studio "uploaded the repositioned
file twice for one start". That was two clicks, not a bug (operator,
2026-09-28). This run shows the same pattern from the other side: two presses,
one blocked and one started.
