# Commissioning run: StitchLabOS v0.1.0-beta.4 on real hardware

> Dated evidence, 2026-09-27. This report is never corrected afterwards; later
> findings go into a new report. The path under test is
> [11-commissioning.md](../11-commissioning.md) as of tag `v0.1.0-beta.4`
> (`fc15e8a`). Acceptance target: Beta2 in [10-roadmap.md](../10-roadmap.md).

## Result in one paragraph

Steps 1, 2 and 4 passed; **step 3 failed as written**. The guide tells the user
to hold a BOOTSEL button that the BTT SKR Pico V1.0 does not have, and
`stitchlab-flash-pico` cannot bring up a Pico that already carries older
Katapult/Klipper firmware. The MCU was brought up with a workaround that uses
only files shipped in the image; after that, a firmware update over the UART
without the USB cable worked first time. Host and MCU run the same Klipper
commit. **The Beta2 acceptance is not met by this run**: step 3 failed, the
Pico was not factory-fresh, and the person doing the physical steps is one of
the authors.

## Step 3 in detail

1. **13:45.** The script stopped at `[sudo] password for pi:` in a terminal
   tab the human did not watch. `sudo` gave up after about 11 minutes
   (`pam_unix(sudo:auth): auth could not identify password`), and the script
   ended **without any message**. The guide does not mention the password
   prompt.
2. **14:55.** Run as the guide says. The script asked to *hold BOOTSEL while
   plugging in*. The SKR Pico V1.0 has no such button: it has a **BOOT
   jumper** and a **RESET button** (Voron docs,
   `docs.vorondesign.com/build/software/skrPico_klipper.html`). After 120 s
   the script fell back to the UART: `FlashError: Error sending command
   [CONNECT] to Device` three times.
3. **15:02.** BOOT jumper on, RESET, USB into the Pi. The first try showed no
   USB device at all, because the plug was not fully seated. After reseating,
   the Pi showed `2e8a:0003 Raspberry Pi RP2 Boot`. The jumper was removed
   before starting the script, because the RP2040 samples BOOT at every reset.
   The script wrote Katapult ("Katapult written — the Pico rebooted"), then
   failed on the UART again with `CONNECT` three times.
4. **15:08.** Double-click on RESET (Katapult's double-reset entry), then
   `stitchlab-flash-pico --uart`: the same `CONNECT` failure three times.

**Pi side ruled out:** `pinctrl get 14,15` gives `a0` = TXD0/RXD0,
`/dev/serial0 → ttyAMA0`, no serial getty, nothing else holding the port,
`[mcu] baud: 115200`.

**Cause:** Katapult starts the application whenever the first word at
`0x10004000` is neither `0` nor `0xffffffff`
(`katapult/src/generic/armcm_canboot.c:61-64`, `application_check_valid()`).
Writing `katapult.uf2` rewrites only the bootloader region. On this Pico the
earlier Klipper build still sat at `0x10004000`, so the new Katapult started it
instead of waiting on the UART. flashtool's reboot-to-bootloader request at
115200 baud got no answer from that old build, whose baud rate and version are
unknown. The double-reset entry did not help either; why it failed was not
investigated.

**Workaround, using only files in the image:** BOOT jumper on, RESET, jumper
off, then

```bash
sudo mount /dev/sda1 /mnt && sudo cp ~/firmware/klipper.uf2 /mnt/ ; sync ; sudo umount /mnt
```

Katapult then found the current Klipper at `0x10004000` and started it. A
`FIRMWARE_RESTART` through Moonraker brought Klipper to `ready`.

On a factory-fresh Pico that word is `0xffffffff` and Katapult stays in the
bootloader, so the script's path should work there. **That was not tested in
this run.**

## Deviations from 11-commissioning.md

1. **§1: `rpi-imager` is not a command on macOS.** It needs
   `/Applications/Raspberry Pi Imager.app/Contents/MacOS/rpi-imager --repo …`.
   The same bare command appears in `README.md`, `08-image-building.md`,
   `stitchlabos/image/README.md` and the release notes.
2. **§1: Imager 2.0.11 applies customisation even when every field is
   skipped.** It wrote `user-data` (timezone Europe/Vienna, keyboard `at`,
   `ssh_pwauth: true`, `systemctl enable --now ssh`, `rfkill unblock wifi`),
   `meta-data`, and appended `cfg80211.ieee80211_regdom=AT ds=nocloud;…` to
   `cmdline.txt`. Harmless here, because the image ships no `user-data` of its
   own and `cmdline.txt` kept `plymouth.ignore-serial-consoles` without
   `console=serial0`. But the guide's "not needed" suggests nothing is written.
3. **§1: Imager's automatic eject did not take.** The card stayed mounted and
   was ejected by hand.
4. **§2: `stitchlab.local` does not exist over Ethernet.** The image sets Avahi
   `allow-interfaces=wlan0` (`stitchlabos/image/src/modules/stitchlabos/start_chroot_script:81-86`).
   A Pi on a LAN cable is reachable by IP only. Over a direct Mac–Pi cable
   without DHCP, NetworkManager gave up on `eth0` after its 45 s DHCP timeouts,
   and the Pi dropped off the link.
5. **§2: a laptop that knew an earlier StitchLab image refuses SSH.** Its
   `stitchlab.local` host key is stale ("REMOTE HOST IDENTIFICATION HAS
   CHANGED"); `ssh-keygen -R stitchlab.local` fixes it.
6. **§3: the script asks for the `pi` password** (`sudo`), and exits silently
   if `sudo` fails.
7. **§3: "hold BOOTSEL" is wrong for the SKR Pico V1.0**, in the guide, the
   README, the release notes and the script's prompt. The board needs the BOOT
   jumper plus RESET, and the jumper must come off again before the Pico
   restarts into the new code.
8. **§3: a Pico that is not factory-fresh cannot be commissioned with the
   script.** The rescue route "Katapult is broken → `--bootsel`" has the same
   gap, because it also leaves the old application in place.
9. **§4: "the axes move after homing".** A job started later from the file
   list failed on its first move with `Must home axis first`, because the
   steppers had idled out. The guide does not say that axes lose their homed
   state after the idle timeout.

## Known issues from the brief, as observed

- **Hoop taller than the machine** (130 mm hoop, Y limited to 120 mm): not
  exercised; the real usable Y travel was not measured.
- **Placement offsets carried into file-list starts:** the intake recorded
  offset 0 and rotation 0 for the file-list start. The blocked test used an
  explicit offset; whether it was reset afterwards was not checked.
- **Dongle LED command:** not tested (no dongle).
- **Image size:** 932 484 116 bytes compressed (release asset), as stated.

## Not covered by this run

- A factory-fresh SKR Pico, and a Raspberry Pi 5. `config.txt` has no
  Pi-5-specific UART line, so `/dev/serial0` on a Pi 5 is unverified.
- All dongle and controller checks.
- Laptop Wi-Fi drop (check 10c).
- A person who is not one of the authors.
